LABORATORIO DI INGEGNERIA DEI SISTEMI SOFTWARE

Introduction

Goal Sprint 3: Sviluppare un'interfaccia web accessibile che permetta al Transport Manager di inviare richieste di deposito (storerequest) e ticket (ticketrequest) al sistema ColdStorageService, visualizzando in tempo reale lo stato del sistema tramite aggiornamenti automatici.
Lo Sprint 3 si focalizza sull'integrazione di un'interfaccia utente moderna e reattiva che sostituisce la GUI simulata degli sprint precedenti, mantenendo inalterata la logica di business del sistema. L'architettura adotta il pattern Facade per semplificare l'accesso al sistema QAK.

Requirements

Requisiti funzionali

  • REQ-GUI-1: L'interfaccia web deve permettere al Transport Manager di inserire il peso (in kg) per una richiesta di deposito
  • REQ-GUI-2: Il sistema deve visualizzare il ticket generato in caso di richiesta accettata, con un countdown timer di scadenza (30 secondi)
  • REQ-GUI-3: L'interfaccia deve permettere l'invio del numero di ticket quando il truck è all'INDOOR
  • REQ-GUI-4: Il sistema deve mostrare lo stato corrente:
    • Peso attualmente depositato nella cold room
    • Capacità massima (200 kg)
  • REQ-GUI-5: Gli aggiornamenti di stato devono essere real-time e automatici, senza necessità di refresh manuale
  • REQ-GUI-6: L'interfaccia deve fornire feedback visivo immediato per ogni azione (richiesta accettata/rifiutata, ticket valido/scaduto)

Requisiti non funzionali

  • REQ-NFR-1: Usabilità: L'interfaccia deve essere intuitiva e accessibile da browser web (Chrome, Firefox, Edge) senza installazioni aggiuntive
  • REQ-NFR-2: Responsività: L'interfaccia deve adattarsi a diversi dispositivi (desktop, tablet, mobile)
  • REQ-NFR-3: Performance: Gli aggiornamenti real-time devono avvenire con latenza < 500ms
  • REQ-NFR-4: Manutenibilità: Il codice frontend e backend devono essere separati e modulari
  • REQ-NFR-5: Compatibilità: Il sistema deve mantenere retrocompatibilità con la logica di business degli sprint precedenti

Requirement analysis

Analisi dei requisiti GUI

1. Interfaccia utente

L'interfaccia deve sostituire il QActor serviceaccessgui degli sprint precedenti mantenendo le stesse funzionalità:

  • Form richiesta deposito: campo input per peso (1-200 kg) + pulsante invio
  • Visualizzazione ticket: card con numero ticket, peso, countdown timer
  • Form invio ticket: campo input per numero ticket + pulsante invio
  • Sezione stato sistema: peso corrente e capacità massima

2. Comunicazione client-server

La GUI deve comunicare con il sistema QAK attraverso un layer intermedio (Facade) che:

  • Riceve richieste dall'interfaccia web via WebSocket (bidirezionale)
  • Inoltra le richieste al sistema QAK via TCP
  • Riceve aggiornamenti di stato dal sistema QAK via CoAP Observer
  • Notifica la GUI in real-time via WebSocket

3. Aggiornamenti real-time

Il sistema deve supportare aggiornamenti automatici per:

  • Peso corrente: quando una richiesta viene accettata o un ticket scade
  • Stato trolley: per eventuali estensioni future (LED warning device)

4. Gestione errori

L'interfaccia deve gestire e visualizzare chiaramente:

  • Richieste rifiutate (peso eccede spazio disponibile)
  • Ticket scaduti (oltre 30 secondi)
  • Ticket non validi
  • Errori di connessione

Problem analysis

1. Architettura Facade Pattern

Perché il pattern Facade?

Il sistema QAK è complesso e richiede conoscenza specifica di:

  • Protocollo TCP per comunicazione attori
  • Sintassi messaggi QAK (storerequest(KG), ticketrequest(TICKET))
  • CoAP per osservare risorse degli attori

Il Facade Pattern semplifica l'accesso fornendo un'interfaccia unificata che nasconde la complessità del sistema sottostante.

Componenti della Facade

Componente Responsabilità Tecnologia
ServiceFacadeController Controller REST/WebSocket Spring Boot
ApplguiCore Logica applicativa Kotlin
ActorOutIn Adapter TCP per comunicazione con QAK Kotlin + unibo.actor22comm
WSHandler Gestione WebSocket per GUI Spring WebSocket

2. Protocolli di comunicazione

WebSocket (GUI ↔ Facade)

  • Porta: 8091
  • Endpoint: ws://localhost:8091/accessgui
  • Formato messaggi da GUI:
    • request/storerequest/storerequest(50)
    • request/ticketrequest/ticketrequest(1)
  • Formato messaggi da Facade:
    • storeaccepted(1, 50.0)
    • storerefused(50.0)
    • chargetaken(1)
    • ticketrefused(1)
    • currentlyStored(50.0)

TCP (Facade ↔ QAK)

  • Porta: 8015 (ctxcoldstorageservice)
  • Formato: Messaggi QAK con intestazione msg(MSGID, TYPE, SENDER, RECEIVER, CONTENT, SEQNUM)
  • Gestito da: ActorOutIn usando unibo.actor22comm.tcp.TcpClientSupport

CoAP (QAK → Facade)

  • Porta: 8015 (stesso del TCP, ma protocollo diverso)
  • Risorse osservate:
    • coap://localhost:8015/ctxcoldstorageservice/coldstorageservice
    • coap://localhost:8015/ctxcoldstorageservice/trolley
  • Trigger aggiornamenti: updateResource negli attori QAK

3. Frontend: tecnologie e design

Stack tecnologico

  • HTML5: struttura semantica dell'interfaccia
  • CSS3: styling moderno con variabili CSS, flexbox, grid, animazioni
  • JavaScript (ES6+): logica client-side, WebSocket API, manipolazione DOM
  • Thymeleaf: template engine per integrazione con Spring Boot

Design pattern frontend

  • Event-driven: listener per eventi WebSocket e form submission
  • Observer pattern: la GUI "osserva" i messaggi WebSocket e reagisce
  • State management: variabili globali per stato corrente (peso, ticket attivo, timer)

User Experience (UX)

  • Feedback immediato: messaggi di successo/errore sotto ogni form
  • Toast notifications: popup temporanei per azioni importanti
  • Countdown timer visivo: cambio colore quando < 5 secondi
  • Animazioni smooth: zoom quando peso si aggiorna, slide-in per toast
  • Responsive design: layout adattivo per mobile/desktop

4. Gestione stato e sincronizzazione

Problema: sincronizzazione peso

Il peso nella cold room può cambiare in 3 scenari:

  1. Richiesta accettata: CurrentLoad += peso
  2. Ticket scaduto: CurrentLoad -= peso (prenotazione annullata)
  3. Carico depositato: peso già conteggiato, nessuna modifica

Soluzione: Il coldstorageservice chiama updateResource in questi punti: 

// State s0 initial
updateResource [# "currentlyStored($CurrentLoad)" #]  // peso iniziale = 0

// State handlestore (richiesta accettata)
if [# LoadToStore <= FreeSpace #] {
    [# CurrentLoad = CurrentLoad + LoadToStore #]
    updateResource [# "currentlyStored($CurrentLoad)" #]
}

// State handleticket (ticket scaduto)
else {
    [# CurrentLoad = CurrentLoad - Load #]
    updateResource [# "currentlyStored($CurrentLoad)" #]
}

Flusso aggiornamento peso

1. coldstorageservice modifica CurrentLoad
   ↓
2. updateResource("currentlyStored(50.0)")
   ↓
3. CoAP Observer (FacadeBuilder) riceve notifica
   ↓
4. CoapObserver.onLoad() → ApplguiCore.handleMsgFromActor()
   ↓
5. WSHandler.sendToAll("currentlyStored(50.0)")
   ↓
6. Browser riceve via WebSocket
   ↓
7. app.js: handleCurrentlyStored()
   ↓
8. updateWeightDisplay(50) → UI aggiornata con animazione

2. Implementazione backend (Facade)

ApplguiCore.kt - Core applicativo

class ApplguiCore(val name: String) {
    val wshandler = WSHandler()
    val actorOutIn = ActorOutIn("actorOutIn", this)
    
    fun handleWsMsg(msg: String) {
        // Parse: "request/storerequest/storerequest(50)"
        val parts = msg.split("/")
        val messageType = parts[0]
        
        when (messageType) {
            "request" -> {
                val requestType = parts[1]
                val content = parts[2]
                // Inoltra al QAK system via TCP
                actorOutIn.dorequest(requestType, content)
            }
        }
    }
    
    fun handleMsgFromActor(msg: String) {
        // Riceve da QAK o CoAP Observer
        // Inoltra a tutti i client WebSocket
        wshandler.sendToAll(msg)
    }
}

ActorOutIn.kt - Adapter TCP

class ActorOutIn(name: String, val appl: ApplguiCore) {
    val conn = TcpClientSupport.connect(host, port, 5)
    
    fun dorequest(requestType: String, content: String) {
        // Costruisce messaggio QAK
        val msg = MsgUtil.buildRequest(
            "gui", requestType, content, "coldstorageservice"
        )
        // Invia via TCP
        conn.forward(msg.toString())
    }
    
    fun handleReplyMsg(msg: IApplMessage) {
        // Reply ricevuta dal QAK system
        val content = msg.msgContent()
        appl.handleMsgFromActor(content)
    }
}

WSHandler.kt - WebSocket

@Component
class WSHandler : TextWebSocketHandler() {
    private val sessions = CopyOnWriteArrayList<WebSocketSession>()
    
    override fun afterConnectionEstablished(session: WebSocketSession) {
        sessions.add(session)
    }
    
    override fun handleTextMessage(session: WebSocketSession, message: TextMessage) {
        val msg = message.payload
        ApplguiCore.handleWsMsg(msg)
    }
    
    fun sendToAll(msg: String) {
        sessions.forEach { session ->
            if (session.isOpen) {
                session.sendMessage(TextMessage(msg))
            }
        }
    }
}

CoapObserver.kt - CoAP

class CoapObserver(val appl: ApplguiCore, val endpoint: String) : CoapHandler {
    
    fun observe() {
        val uri = URI(endpoint)
        val client = CoapClient(uri)
        client.observe(this)
    }
    
    override fun onLoad(response: CoapResponse) {
        val content = response.responseText
        // Esempio: "currentlyStored(50.0)"
        appl.handleMsgFromActor(content)
    }
}

// Connessione WebSocket
function connectWebSocket() {
    socket = new WebSocket("ws://localhost:8091/accessgui");
    
    socket.onopen = () => {
        showToast('Connesso al server', 'success');
    };
    
    socket.onmessage = (event) => {
        handleServerMessage(event.data);
    };
}

// Parsing messaggi
function handleServerMessage(message) {
    if (message.includes("storeaccepted")) {
        handleStoreAccepted(message);
    }
    else if (message.includes("currentlyStored")) {
        handleCurrentlyStored(message);
    }
    // ...
}

// Aggiornamento peso con animazione
function updateWeightDisplay(weight) {
    const el = document.getElementById("currentWeight");
    el.classList.add('updating');
    el.textContent = `${weight} kg`;
    
    const percentage = (weight / MAXW) * 100;
    if (percentage < 50) el.classList.add('weight-low');      // verde
    else if (percentage < 80) el.classList.add('weight-medium'); // arancione
    else el.classList.add('weight-high');                     // rosso
    
    setTimeout(() => el.classList.remove('updating'), 500);
}

// Toast notifications
function showToast(message, type, duration = 3000) {
    const toast = document.createElement('div');
    toast.className = `toast ${type}`;
    toast.innerHTML = `<span>${emoji}</span><span>${message}</span>`;
    document.getElementById('toastContainer').appendChild(toast);
    
    setTimeout(() => {
        toast.classList.add('removing');
        setTimeout(() => toast.remove(), 300);
    }, duration);
}
